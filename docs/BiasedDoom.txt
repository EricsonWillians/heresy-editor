HERESY EDITOR AND BIASEDDOOM
============================

Purpose
-------

Heresy Editor is being developed as a Doom-family map editor with BiasedDoom as
its primary target engine.  BiasedDoom is derived from GZDoom and retains the
standard IWAD, WAD, PK3, ZDoom map-format and command-line interfaces used by
the editor's existing test-map workflow.  Heresy Editor creates and edits both
direct WAD projects and PK3 projects with maps stored at `maps/<slot>.wad`.


Current support
---------------

Use the `biaseddoom` source-port profile for BiasedDoom projects.  It derives
from the shared ZDoom definitions and provides Doom, Hexen and UDMF map formats,
the ZDoom namespace, common ZDoom things and action specials, dynamic-light
definitions, and support for Doom, Doom II, Heretic, Hexen, and Strife.

For a new project, choose WAD package for maximum classic-port compatibility or
PK3 package for a BiasedDoom/GZDoom-style mod.  Campaign layout can follow the
IWAD, contain one map, or use a custom ordered list.  Heresy Editor's Tools /
Test in Game command invokes the selected engine with:

- the project IWAD via `-iwad`;
- resource files and the edited WAD or PK3 via `-file`; and
- the current map via `-warp`.

Those arguments are supported by BiasedDoom.  Tools / Test in Game keeps an
existing valid engine selection.  Otherwise it searches these bounded,
non-recursive locations in order:

1. the explicit `BIASEDDOOM_EXE` environment variable;
2. each directory in the process `PATH`;
3. an executable beside the editor or in the same installation prefix;
4. common single- and multi-configuration CMake build directories under a
   sibling checkout, `~/workspace/BiasedDoom`, or `~/BiasedDoom`; and
5. conventional per-user and system installation locations.

A typical local development build in this workspace is:

    ~/workspace/BiasedDoom/build/biaseddoom

The exact output directory can vary with the BiasedDoom CMake generator and
build configuration.  Windows builds use `biaseddoom.exe`; packaged macOS
application bundles and Linux AppImages are recognized.  Invalid or stale
candidates are skipped.  If automatic discovery finds nothing, Heresy Editor
opens the engine picker and remembers the user's selection as before.

An explicit project's adjacent `.heresy` file restores its active map,
Campaign Navigator selection, and portable IWAD hint.  Keep that file beside
the WAD or PK3 when relocating the project.  It contains no gameplay data or
absolute IWAD path and is never passed to BiasedDoom.


Known boundary
--------------

The BiasedDoom 4.15.7 metadata inventory found no engine-only DoomEdNums,
action specials, or UDMF namespace to add.  Procedural generation uses stock
Doom/Doom II things and established ZDoom specials.  Renderer settings, Python
integration, glTF models, and related extensions remain external resource or
runtime features.  The extended line, side, and sector properties emitted by
the generator now survive UDMF load/edit/save cycles; see
`docs/BiasedDoomInventory.txt` for the audited list and reproducible check.


Compatibility roadmap
---------------------

1. Complete: add a named BiasedDoom port profile derived from the ZDoom
   definitions, executable discovery, and launch regression coverage.
2. Complete: inventory BiasedDoom-only editor numbers, specials and namespaces.
   BiasedDoom 4.15.7 adds none; generator coverage is regression-tested.
3. Complete: preserve the relevant established ZDoom UDMF properties without
   changing classic Doom or Hexen serialization.
4. Complete: exercise dirty Doom, Hexen and UDMF maps through the full Tools /
   Test in Game save, node-build, argument, and launch path.
5. Next: keep the profile synchronized with BiasedDoom releases.


Legacy identifiers
------------------

The executable is `heresy`.  The fork retains inherited `eureka` configuration
paths and the `EUREKA` WAD lump so existing projects and settings continue to
work; those compatibility identifiers do not change the product name.
