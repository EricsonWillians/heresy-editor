HERESY EDITOR AND BIASEDDOOM
============================

Purpose
-------

Heresy Editor is being developed as a Doom-family map editor with BiasedDoom as
its primary target engine.  BiasedDoom is derived from GZDoom and retains the
standard IWAD, WAD, PK3, ZDoom map-format and command-line interfaces used by
the editor's existing test-map workflow.  Heresy Editor creates and edits both
direct WAD projects and PK3 projects with maps stored at `maps/<slot>.wad`.


Current support
---------------

Use the `biaseddoom` source-port profile for BiasedDoom projects.  It derives
from the shared ZDoom definitions and provides Doom, Hexen and UDMF map formats,
the ZDoom namespace, common ZDoom things and action specials, dynamic-light
definitions, and support for Doom, Doom II, Heretic, Hexen, and Strife.

For a new project, choose WAD package for maximum classic-port compatibility or
PK3 package for a BiasedDoom/GZDoom-style mod.  Campaign layout can follow the
IWAD, contain one map, or use a custom ordered list.  New Project presents
project settings, campaign/resources, and review/create as separate pages; its
final summary validates the new destination before any package is written.
Campaign Navigator can attach display titles and episode labels to configured
maps, mark additional campaign entry points, and model normal and secret routes.
The first configured slot remains an implicit entry, and Create Next Map follows
the current map's normal route.  The navigator analyzes the same route graph
from every entry and flags unreachable maps, potential cycles, and configured
route targets that are missing from the project package.  The selected-map
panel identifies the involved routes and corrective Create or Map Details
action.  This is
editor project metadata until File / Generate Runtime MAPINFO is explicitly
run.  That command previews a marker-owned root ZMAPINFO for BiasedDoom,
GZDoom, or ZDoom, including campaign entries, titles, routes, and endings.
Missing titles visibly fall back to map-slot names.  Generation refuses all
user-authored MAPINFO-family declarations instead of overwriting them; only a
previously generated marker-owned declaration can be updated.

PK3 projects expose resources recursively below the conventional `flats/`,
`sprites/`, and `textures/` directories in the editor browser.  The projection
uses WAD-compatible basenames only; saves retain each resource's complete PK3
path and archive record. File / Import Surface Textures is the explicit
exception: after a decoded conflict review, it can add or unambiguously replace
individual `textures/<name>.<extension>` and `flats/<name>.<extension>` entries
without rewriting unrelated archive records. Modern images can target walls,
floors/ceilings, or both and become immediately available to ordinary controls,
Smart Door, and Smart Sector. See `docs/SurfaceTextures.txt`.
File / PK3 Metadata provides a separate read-only archive inventory.  It shows
MAPINFO-family and common resource declarations verbatim, lists runtime sources
without interpreting them, summarizes conventional resource directories, and
accounts for managed and otherwise preserved files.  Binary, unreadable, and
oversized declarations are reported without unsafe preview attempts.  The same
view reports duplicate uppercase eight-character flat, sprite, and texture
names within the PK3 and overrides across the loaded IWAD, resources, and
project.  It shows complete package paths and nominal winners where resolution
is deterministic, while sprite-frame combinations remain explicitly ambiguous;
it never renames entries or changes source order.

Tools / Test in Game invokes the selected engine with:

- the project IWAD via `-iwad`;
- resource files and the edited WAD or PK3 via `-file`; and
- the current map via `-warp`.

Those arguments are supported by both engines.  Tools / Test in Game keeps an
existing valid engine selection.  Otherwise the BiasedDoom profile prefers
BiasedDoom and falls back to GZDoom; the shared ZDoom profile uses the opposite
preference.  Discovery searches in this order:

1. the explicit `BIASEDDOOM_EXE` and `GZDOOM_EXE` environment variables;
2. each directory in the process `PATH`;
3. an executable beside the editor or in the same installation prefix;
4. common single- and multi-configuration CMake build directories under a
   BiasedDoom or GZDoom checkout; and
5. a recursive, permission-tolerant search of likely workspace, application,
   home, editor-installation, and platform installation roots.

A typical local development build in this workspace is:

    ~/workspace/BiasedDoom/build/biaseddoom

The exact output directory can vary with the CMake generator and build
configuration.  Windows `.exe` builds, packaged macOS application bundles,
Linux extensionless executables, and AppImages are recognized.  Recursive
matching is case-insensitive and does not follow directory symlinks.  Invalid,
stale, or non-executable POSIX candidates are skipped.  Deep searches run on a
worker behind a responsive progress dialog showing the current location,
folder count, and candidate count, and can be cancelled at any time.  If
discovery finds nothing, Heresy Editor opens an extension-neutral engine picker
and remembers the selection; no `.exe` suffix is required.  Test Settings keeps
that path directly editable and offers separate Browse and Auto Detect actions.
An inline status distinguishes an empty or missing path, a folder, a
non-executable Unix file, an inaccessible path, and a ready executable.
Cancelled or unsuccessful rediscovery preserves the existing selection.

Saving before launch does not reset the active document's Undo or Redo
history.  Test in Game returns keyboard focus to the map canvas, so the tested
edit can be undone immediately with Ctrl/Cmd+Z.  Edit -> Redo,
Ctrl/Cmd+Shift+Z, or Ctrl/Cmd+Y restores an accidental Undo until another edit
replaces the redo future.

For explicit BiasedDoom/GZDoom/ZDoom projects, Campaign Navigator also labels
managed runtime ZMAPINFO as current or out of date.  Test in Game compares the
marker-owned content with the declaration that current in-memory campaign
metadata would generate.  Stale output offers Cancel, Launch Anyway, or Review
and Update; the last choice uses the same exact preview, project save, conflict
recheck, and atomic package write as File / Generate Runtime MAPINFO.  Missing
runtime declarations remain optional and user-authored MAPINFO is not compared,
prompted for, or rewritten.

An explicit project's adjacent `.heresy` file restores its active map,
Campaign Navigator selection, and portable IWAD hint.  Keep that file beside
the WAD or PK3 when relocating the project.  It contains no gameplay data or
absolute IWAD path and is never passed to BiasedDoom.


Known boundary
--------------

The BiasedDoom 4.15.7 metadata inventory found no engine-only DoomEdNums,
action specials, or UDMF namespace to add.  Procedural generation uses stock
Doom/Doom II things and established ZDoom specials.  Renderer settings, Python
integration, glTF models, and related extensions remain external resource or
runtime features.  The extended line, side, and sector properties emitted by
the generator now survive UDMF load/edit/save cycles; see
`docs/BiasedDoomInventory.txt` for the audited list and reproducible check.
Established ZDoom surface panning/scaling/rotation fields are also editable
through Edit / Surface Texture Transform and rendered consistently in
OpenGL/software preview; see `docs/SurfaceTransforms.txt`.


Compatibility roadmap
---------------------

1. Complete: add a named BiasedDoom port profile derived from the ZDoom
   definitions, executable discovery, and launch regression coverage.
2. Complete: inventory BiasedDoom-only editor numbers, specials and namespaces.
   BiasedDoom 4.15.7 adds none; generator coverage is regression-tested.
3. Complete: preserve the relevant established ZDoom UDMF properties without
   changing classic Doom or Hexen serialization.
4. Complete: exercise dirty Doom, Hexen and UDMF maps through the full Tools /
   Test in Game save, node-build, argument, and launch path.
5. Complete: pin the audited BiasedDoom release contract and monitor GitHub's
   latest published release weekly for compatibility drift.


Legacy identifiers
------------------

The executable is `heresy`.  The fork retains inherited `eureka` configuration
paths and the `EUREKA` WAD lump so existing projects and settings continue to
work; those compatibility identifiers do not change the product name.
